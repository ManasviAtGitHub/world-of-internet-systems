The Hash Table

The most-used data structure on earth, and the most-misquoted promise in interviews: "O(1)". The truth has two asterisks this page makes you watch. First, the speed is a function of emptiness — probes cost about 1/(1−α), so the last 10% of a table's space costs more than the first 90%. Second, that "expected" in expected O(1) is doing legal work: it's an expectation over the hash's randomness, and an adversary who can predict your hash gets to repeal it. Predict first, then run it. That's the rep.

Everything below computes for real: the hero is an actual linear-probing table cross-checked against a shadow map on every sample, the probe curve is measured off a real 8,192-slot table sweeping to α = 0.98, and the flooding attack really does grow one chain and starve a real work queue.

Space
O(n) plus deliberate slack — the table is fastest when partly empty
Time
O(1) expected lookup/insert · O(n) worst case · resize O(n), amortized away
The catch
speed is a function of load factor α — and "expected" assumes the hash's randomness, which an adversary can take away

The number that runs the show

One symbol governs everything you just watched: α = n/m, keys over slots. Collisions aren't a malfunction — with random hashing they're guaranteed (that's the birthday paradox: 23 keys in 365 slots already collide more often than not). What matters is how often, and the classic analysis gives the pocket law: an absent-key lookup in an open-addressed table expects about 1/(1−α) probes. At half full, 2 probes. So here is the prediction: at what load factor does an absent-key lookup cost ~10 probes — five times worse than half-full? Intuition says performance degrades gently. Commit to a button, then a real 8,192-slot table sweeps its α upward and measures.

What "amortized" feels like in production

The resize you watched in the hero was cute at 48 slots. Now scale it: a session store holding a few hundred thousand entries doubles, and every key must rehash right now — while requests keep arriving. The stalls get rarer as the table grows, but each one is twice as big: amortized analysis averages the pain, production feels the spikes. This is a real disease with a famous cure: Redis rehashes incrementally — it keeps both tables during migration and moves a bucket or two per operation, so no single request ever pays for the whole move. The Board episode's memcached wall lives on the same principle: the cache tier can't afford stop-the-world anything.

Whose expectation is "expected O(1)"?

The textbook promise averages over the hash function's randomness. But if an attacker knows your hash, the average is irrelevant — they can manufacture thousands of keys that all land in one bucket, turning your O(1) table into an O(n) list and your CPU into their weapon. This actually happened: in 2011, researchers demonstrated hash-flooding denial-of-service against PHP, Java, Python and friends — a few hundred kilobytes of crafted POST data could pin a server for minutes. The fix the world adopted (SipHash, now inside Python, Rust, Redis and more) is a keyed hash: a secret seed the attacker can't predict, which restores the randomness the proof needed. The keeper

The keeper: a hash table trades order for speed, and its speed is a function of emptiness and unpredictability — probes ≈ 1/(1−α), resizes are the amortized bill arriving all at once, and "expected O(1)" survives only while the hash stays secret from your adversary. When an interview asks for O(1) anything, this is the shape; when it asks what could go wrong, this page was the answer.

The revision card — for the you that comes back in three months
  • Why is a hash table fastest when partly empty? (probes ≈ 1/(1−α) — you watched 90% full cost 10×)
  • What does "amortized O(1)" hide, and what's the production fix? (the growing resize stall — Redis migrates a bucket at a time, both tables live)
  • Whose expectation is "expected O(1)"? (the hash's randomness — a predictable hash let one bucket become the whole table)
  • When is a hash table the wrong answer? (ranges, prefixes, ordering — hashing destroys order by design; the trie and B-tree pick up that work)
