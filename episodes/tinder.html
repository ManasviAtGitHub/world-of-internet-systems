The Swipe

Dating is local — a user in California never needs a London profile — so Tinder cut the world itself into shards: map cells sized so that Tokyo's tile is tiny and Wyoming's is enormous, and every one holds about the same number of people. Underneath, 1.6 billion daily swipes flow through a stream where a match is not a database join but an O(1) cache probe — and the "It's a Match!" moment arrives as a five-byte nudge down a WebSocket that replaced two-second polling from every open phone on Earth.

Everything below is honestly simulated: the map cells come from a real density-adaptive subdivision of a synthetic world, the cell-size dial traces a genuine cost minimum (fan-out overhead vs index size — the model is stated in the note), the double-swipe race is a true check-then-insert interleaving, and the polling arithmetic is division.

One index for Earth, or a dial with a sweet spot

Tinder's original design kept every profile in one Elasticsearch index — and every query paid for the whole planet's index structures to find neighbors within a few miles. Geosharding fixed it (the published result: roughly 20× the query capacity from the same hardware) — but it opened a genuinely interesting dial. Make cells too big and each query rummages through an oversized index again. Make them too small and every search circle straddles borders, fanning out to many shards, each charging fixed per-shard overhead and a merge. Somewhere in between is a real minimum — not a metaphor, a curve — and the slider below traces it against this world's actual geometry.

Two right swipes, eighty milliseconds apart

The write side is a river: over a billion and a half swipes a day. Left swipes flow to cheap archive storage. A right swipe asks one question — did they already like me? — and the obvious implementation is a read-modify-write: check the likes store, then insert my like. But "check then insert" has a seam, and the sweetest moment in the product lives exactly on it: two people swiping right on each other at nearly the same instant. Both checks run before either insert lands. Both see nothing. Both likes are recorded, no match is ever created, and neither person will ever know. Tinder's pipeline closes the seam by serializing: swipes flow through a stream partitioned by the pair, one worker owns each pair's order, and the second swipe — even a millisecond later — always sees the first.

Anything new? Anything new? Anything new?

Until 2019, every open Tinder app asked the server "anything new?" every two seconds — and the answer was almost always no. The arithmetic of polite polling is brutal: half your users' request rate exists to deliver silence. The replacement holds one WebSocket per open app, and when something actually happens — a match, a message — a gateway pushes a tiny protobuf Nudge: not the data, just "something's new," after which the client fetches through the normal API. Nudges are best-effort on purpose: a lost one is healed by the next event or by a slow fallback sync, which keeps the realtime tier stateless and forgiving.

What the swipe teaches

Tinder's stack is a tour of this series' greatest hits wearing one product: Kafka partitioned by user so a moving profile's updates replay in order (episode 4's log, keeping episode 22's promise), Elasticsearch sharded by the planet itself, a match pipeline that turned a join into a stream plus a cache (episode 17's shield, pointed at romance), and a realtime tier that learned WhatsApp's lesson about connections and Slack's about edges. The ranking beneath — swipe-embedding vectors since 2017, deep models and kNN after the Elasticsearch 8 migration — rides on the same geosharded index, re-validated years later: 12% of CPU with geosharding against a projected 50% without.

The keeper: when your queries are local, shard by the world — cut cells to equal people, accept the border fan-out, and let geography do the load balancing. And never let a race decide whether two people who chose each other get to know it.
