The LSM Tree

The structure that made writes cheap by refusing to edit anything. It never updates a byte in place: it appends to RAM, sorts there, flushes immutable sorted files, and quietly re-merges them forever. That bargain — sequential-only disk writes, paid for later in "compaction" — is the engine under Discord's trillion messages (ScyllaDB), LinkedIn's feed (RocksDB), and half the storage engines this series has touched. The bill it defers has a name: write amplification. Predict it before you run it. That's the rep.

Everything below computes for real: the machines are actual LSM trees holding sorted integer runs — every flush, merge and compaction below moves real keys and counts real bytes. No write amplification number on this page is scripted.

The bargain

A disk (even an SSD) loves sequential writes and punishes random ones — the Kafka episode was built on that single fact. A B-tree pays the random-write price on every update: find the page, edit it in place. The LSM tree refuses: updates go to a sorted structure in RAM, and the disk only ever receives large, sequential, immutable files. Reads got more complicated — a key could now live in any level — and that is exactly the disease The Filter treats: one Bloom filter per run turns "probe every file" into "probe the one that matters."

But the deferred bill is real. When level 1 overflows, one of its files is merged into the ~10 overlapping files of level 2 — rewriting roughly eleven bytes to move one. Every level charges that toll again. So here is the prediction: a leveled LSM tree, fanout 10, three levels deep. In steady state, how many bytes hit the disk for every byte you write? Commit, then watch a real one count.

Two ways to pay the same bill

Compaction strategy is the knob real operators fight about, and the Guild episode's ScyllaDB exposes it directly. Size-tiered compaction merges runs of similar size when enough pile up — lazy, cheap on writes, but old versions of a key linger in many overlapping runs, so space balloons and reads probe more files. Leveled compaction (RocksDB's default style for read-heavy work) keeps each level as one sorted, non-overlapping range — tight space, few probes, but the merge toll is charged eagerly. Below, both strategies eat the identical update stream — same keys, same order — and every number is measured off the real runs.

You can't outrun the invoice

Every byte you ingest obligates the machine to ~WA bytes of future merge work. If writes arrive faster than compaction bandwidth can pay that debt, level 0 piles up — and real engines respond by stalling your writes. RocksDB ships exactly this: when L0 files cross a threshold, ingestion is throttled, then stopped. The experiment below gives a real LSM tree a fixed compaction budget and hands you the ingest dial. There is a hard ceiling on sustained throughput, it equals budget ÷ write amplification, and no burst schedule negotiates with it.

The keeper

The keeper: the LSM tree converts random writes into sequential ones by never editing anything — and charges you write amplification, roughly fanout per level, on a deferred invoice called compaction. Fast writes, Bloom-shielded reads, and a hard throughput ceiling at budget ÷ WA: that's the whole personality of the storage engine under half this series.

The revision card — for the you that comes back in three months
  • Why are LSM writes fast? (append + RAM sort + sequential flush — nothing is ever edited in place)
  • Where does write amplification come from, and how big is it? (each level descent re-merges the neighborhood: ~fanout per level — you measured ~30×)
  • Size-tiered vs leveled: what do you buy, what do you pay? (tiered: cheap writes, bloated space, more probes · leveled: eager merges, tight space, clean reads)
  • Why does every LSM engine ship Bloom filters? (a key could be in any level — The Filter turns probe-everything into probe-one)
  • What caps sustained ingest? (compaction budget ÷ WA — the stall lamp, not the disk's write speed)
