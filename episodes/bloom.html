The Filter

You've revised Bloom filters before — probably from a table of formulas, probably twice, probably forgotten twice. This time, meet the structure where it actually lives: guarding the disks under Discord's messages, sitting inside LinkedIn's feed storage, deciding what a CDN bothers to cache. A Bloom filter is a bit array that's allowed to lie — in exactly one direction — and that single asymmetry is worth billions of disk seeks a day. Predict first, then run it. That's the rep.

The Toolbox is DSA revision anchored to the 30 systems of this series: one structure per piece, honestly simulated, with a prediction to make before you run and backlinks to every episode where you've already met it under fire.

  • "Dedupe a stream too big to store." · "Have we crawled this page before?"

PATTERN: hashing · bit manipulation · probability  ·  SPACE: m bits for n keys, ~10 bits/key for 1% error  ·  TIME: O(k) per op, k hash functions  ·  THE CATCH: no deletes, no false negatives, tunable false positives

The rep: predict before you run

Here's the revision mechanic this tier is built on. The classic production configuration is 8 bits per key with 6 hash functions — it's what you'll find as the default in LSM storage engines. Before you touch anything: a million keys go in, a million absent keys get queried. What fraction get a false "yes"? Commit to an answer. The measurement — a real filter, thousands of real probes — will grade you, and then show you the whole curve you were standing on.

Where it lives: the disk seek you didn't do

Now the production story. LSM storage engines — Cassandra and ScyllaDB under Discord's trillion messages (EP 17), RocksDB under LinkedIn's feed indexes (EP 28) — keep data in layers of immutable sorted files. A read might have to check six files to conclude a key doesn't exist, and in real workloads most lookups are for keys that don't exist (the empty channel, the user with no unread state). Six disk seeks to say "nothing here" is how storage engines drown. So every file carries a Bloom filter in RAM: ask the filter first, and 99% of the pointless seeks die as a one-bit "no." The filter's one-way honesty is what makes this safe — it can waste a seek, but it can never hide your data.

The one-hit wonder problem

Second production story, from the edge. Back in EP 15 the cache funnel absorbed 90% of a CDN's traffic — but there's a dirty secret in edge caches: measured across real CDNs, most objects are requested exactly once. Cache on first touch and these one-hit wonders flood your LRU, evicting the popular objects that were earning their keep, and burning an SSD write for content nobody will ask for again. Akamai's fix (published 2015): a Bloom filter remembers what's been seen before, and the cache only admits an object on its second request. The wonders never come back, so they never get in.

What it cannot do

Revision honesty: the filter's magic has hard edges. You cannot delete — clearing a bit might erase someone else's key, turning the one impossible lie (a false "no") into a real one; systems that need deletion pay double with counting filters, or rebuild periodically (LSM engines get this free, since their files are immutable — which is exactly why the two structures are soulmates). It cannot enumerate its members, cannot say how many times it saw something, and it degrades as it overfills — past its design load the false-positive rate climbs the curve you measured in REP-01. When you need counts, sketches (Count-Min) are next door; when you need "roughly how many distinct," that's HyperLogLog. Same family: trade exactness for a size that fits in RAM, and know the price to four decimal places.
