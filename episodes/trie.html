The Trie

The structure where the key is the path. A trie never hashes and never compares whole keys — it walks one character at a time, and every shared prefix is stored exactly once, no matter how many words lean on it. That gives it the two superpowers a hash table can't have: it answers "what starts with…" (every autocomplete box) and "what's the longest match…" (every IP router on the path of every packet you've ever sent). Lookup costs the key's length — the size of the table never appears in the bill. Predict first, then run it. That's the rep.

Everything below computes for real: the tries are actual linked-node structures built from a real embedded word list, the node counts are counted (with the invariant nodes ≡ unique prefixes re-verified on every insert), and the routing table's longest-prefix answers are cross-checked against a brute-force scan on every single lookup.

The shape of the savings

A trie's economics ride on one question: how much do your keys overlap? English overlaps a lot — construct, construction, consult, consume share their spines, and whole families hang off re-, con-, inter-. Random keys share only what the pigeonhole forces on them. So before the meter runs, commit: the word list this page ships — a few hundred real English words, a few thousand characters flat — how many trie nodes does it actually need, as a fraction of storing every character of every word? After you find out, the same experiment builds a second trie from random gibberish with the exact same word-length profile, so you can see what your savings were made of.

The router in the walls

Every packet you have ever sent was routed by the question "which table entry has the longest prefix matching this address?" — the Border episode ran the whole drama of where those entries come from. The answering machine is a binary trie: walk the address bit by bit, remember the deepest entry passed, and when the path runs out, that memory is the route. Linux ships exactly this (fib_trie, a level-compressed trie); hardware routers bake it into silicon. The alternative — scan the whole table per packet — is the bar to beat, so the experiment runs both on every lookup and lets them vouch for each other.

The catch, and the compressed cure

The trie's honest weakness is memory: a node per character means a pointer-heavy object per letter, and long unbranching chains — -ational, -ization — waste a node on every step where no decision happens. The 1968 fix is still the production fix: collapse every chain into a single edge carrying the whole substring (the Patricia / radix tree). Nothing about lookups changes except the bill: decisions cost nodes, spelling costs bytes. Linux's fib_trie is a level-compressed variant; modern databases use ART, an adaptive radix tree, as an in-memory index. The keeper

The keeper: a trie turns the key itself into the address — O(key length) lookups that never hear how big the table is, prefix queries a hash table can't express, and a memory bill equal to exactly the prefixes your keys don't share (which compression then refuses to pay per letter). When the interview says autocomplete, prefix, or longest-match, this is the shape; when a packet leaves your machine, it's already running.

The revision card — for the you that comes back in three months
  • What does a trie lookup cost, and what does it never cost? (the key's length; the table's size — 8,000 routes still walked in ~24 bits)
  • Which two queries does it own that a hash table can't ask? (prefix enumeration and longest-prefix match — autocomplete and routing)
  • Where do the savings come from — the trie or the keys? (the keys: English shared well over a third; random gibberish shared almost nothing)
  • What's the memory catch and the production fix? (a node per character; radix/Patricia merges chains so nodes buy decisions, not spelling)
