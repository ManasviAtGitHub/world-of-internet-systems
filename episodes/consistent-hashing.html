The Hash Ring

A cache fleet has a strange constitution: every client must know which server holds every key, nobody is allowed to keep a directory, and servers die without notice. The obvious answer — hash the key, take it mod N — works perfectly, right up until the moment N changes. Then it destroys almost everything you cached, all at once.

Every dot below is one cached key. Amber pulse = served from cache. Red pulse = cache miss — the database behind the cache pays for it. The simulations are honest: ownership comes from real hash arithmetic, not a script.

The rule everyone can compute alone

The problem consistent hashing solves is coordination-free agreement. A memcached client in one datacenter and another client on the other side of the fleet must both compute, in microseconds, the same answer to "which server owns user:8123?" — without asking a directory service that would itself become the bottleneck.

hash(key) mod N is the obvious rule: deterministic, perfectly balanced, one line of code. Its flaw is arithmetic, not implementation. Change N from 6 to 5 and hash mod 6 and hash mod 5 agree only about one time in five — so losing one server reassigns roughly four out of five keys fleet-wide. Every reassigned key is a cache miss, and every miss lands on the database the cache was built to protect. The industry name for what happens next is a cache stampede.

In 1997, Karger and colleagues published the fix — invented for early web caching, a decade before Amazon's Dynamo made it famous (Karger et al., STOC 1997). Hash servers and keys onto the same circle; each key belongs to the next server clockwise. Now a dead server's keys slide to its neighbor, and nothing else moves. Below, the same 120 keys live in both worlds. One button kills the same server in each. Watch who panics.

The endurance test: rolling restarts

One failure is survivable in any design. Real fleets churn constantly — deploys, kernel patches, autoscaling, spot instances reclaimed. A rolling restart cycles through every server, one at a time. Below, both worlds endure one: a server goes down, comes back, and the next goes down, every five seconds, forever. Averages tell the story.

The catch: the ring is lumpy

Random points on a circle are not evenly spaced. With one point per server, some server always wins a huge arc and some server starves — the ring balances eventually, on average, which is no comfort to the one machine holding 30% of your keys. Amazon's Dynamo popularized the fix (DeCandia et al., SOSP 2007): give each server not one position but V — virtual nodes — so its territory becomes many small slivers scattered around the circle, and the law of large numbers grinds the lumps flat. Bonus: a machine with twice the hardware simply gets twice the virtual nodes, and proportional load falls out for free.

Where you've already met the ring

Ketama brought the ring to memcached clients in 2007 and it became the default answer for cache fleets. Dynamo built a whole database on it, and its descendants — Cassandra, Riak, DynamoDB — still route by ring, virtual nodes and all. CDNs use it to keep each URL cached at a consistent edge machine. Envoy offers ring hashing for session-sticky service routing. And when Google needed per-packet routing at line rate, Maglev traded the ring for a precomputed 65,537-slot lookup table — accepting slightly more disruption on membership change in exchange for near-perfect balance and O(1) lookups (Eisenbud et al., NSDI 2016) — proof that even the classics are a point on a trade-off curve, not the end of it.

The deeper pattern to keep: decouple the name from the place. Mod-N welds a key's identity to the current shape of the fleet, so the fleet can't change shape without breaking every promise. The ring — like Notion's logical shards, like Maglev's table — puts a stable layer of indirection in between, so machines can come and go while the names stay put. You will meet this move again in almost every episode of this series.
