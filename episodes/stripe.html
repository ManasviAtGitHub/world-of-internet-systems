The Charge

The network under every payment promises only "at least once" — and money is the one workload where "at least once" means "sometimes twice." Stripe's whole engineering identity grew from taking that seriously: the idempotency key that made retries safe enough to become the industry's standard pattern, rate limiters that throw test traffic overboard before touching a real charge, and an API where an integration written in 2011 still runs, unchanged, against fourteen years of breaking changes. $1.4 trillion moved across this design in 2024 — about 1.3% of global GDP.

Everything below is honestly simulated: both retry worlds face identical seeded failures, the load shedder allocates real capacity in priority order, and the version time machine actually applies each dated transformation to a live response object.

Exactly once, over a wire that promises at least once

Here is the nightmare in one sentence: you charge a card, the response never arrives — did it happen? If you retry blindly, and the charge did happen, the customer pays twice. If you never retry, and it didn't, you lost the sale. The network cannot tell you which world you're in; there are three distinct ways to be ambiguous (the request died on the way, the server died mid-work, the response died on the way back), and only one of them is safe to retry naively. Stripe's answer — published in 2017 and copied by essentially every payments API since — is the idempotency key: the client names each logical operation with a unique key and retries with the same key; the server records the outcome atomically with the work, and any repeat of a completed key gets the recorded response instead of a second execution. Retries become free. Below, both worlds face the exact same failures.

Throw the test traffic overboard first

Black Friday 2024 peaked at 137,000 transactions a minute. When demand outruns capacity, the question isn't whether to drop traffic — it's what to drop first, and Stripe's published answer is a four-layer bouncer: a per-user token bucket (no single key may monopolize the fleet), a concurrency limiter for expensive calls, a reserved slice of capacity that only charge-critical methods may use, and a worker-utilization shedder that jettisons traffic in strict priority order — test-mode requests first, then reads, then ordinary writes, and never the charges. New limiters are dark-launched: they log what they would have blocked, for weeks, before they're allowed to block anything.

The version time machine

Stripe's strangest promise: an integration written against the 2011 API still works today, and yet the API has shipped roughly a hundred backwards-incompatible changes. The trick is that "version" isn't v1/v2 — it's a date. Your account is pinned to the version in force at your first request, forever. Internally, every breaking change is a module with a date and a transformation function; the server always renders responses in the newest shape, then walks them backward through the stack of modules — un-renaming fields, re-nesting objects — until the response matches your pinned year. New customers get the future; old customers get 2011, freshly computed.

The monolith and the ledger

Two more heresies complete the picture. While the industry split into microservices, Stripe kept one giant Ruby codebase and made it survivable by building Sorbet — a static type checker fast enough for 15 million lines in 150,000 files, open-sourced in 2019 and now Ruby's standard. And beneath every product sits Ledger: all money movement modeled as state machines emitting immutable events — five billion a day — into double-entry bookkeeping where every flow must clear to zero. Not reconciliation scripts hoping to catch drift: continuous, measured proof, with 99.9999% of money movement automatically explained. Accounting's 700-year-old invariant, running as a distributed systems test.

The keeper: Stripe's edge is treating the sharp edges of distributed systems — retries, overload, versioning — as product surfaces with published guarantees, so that the scariest possible workload behaves like a database transaction.
