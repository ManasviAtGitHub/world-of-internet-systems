World of Internet Systems · The Flagships · Episode 13

The Feed

Instagram is the proof that boring technology scales: three engineers rode plain Django, PostgreSQL, and Redis to fourteen million users. Their one genuinely clever invention was a number — a 64-bit ID that carries its own timestamp, its own shard address, and its own sequence inside itself, minted by the database with no coordination at all. This episode takes that number apart, live, and shows what it buys a feed.

Every ID below is real 64-bit arithmetic (BigInt, actually computed and actually decoded). The layout is Instagram's published one: 41 bits of milliseconds, 13 bits of shard, 10 bits of sequence — 1,024 IDs per shard per millisecond.

Why not just ask an ID server?

Twitter solved the same problem with Snowflake — a fleet of dedicated ID servers. That works, but it's a service: something to deploy, monitor, and lose. For a three-engineer team, every network hop in the write path is a tax and every dependency is a pager. Instagram's move was to make the ID a property of the shard itself: the database mints it in the same transaction that inserts the row. The experiment below runs both designs against the same posting traffic — then breaks the ID service.

What the number knows

The layout isn't just compact — each field does live work. Because the timestamp owns the top bits, ORDER BY id is ORDER BY created_at: the feed's reverse-chronological sort needs no second column and no second index. And because the shard ID is embedded, any server holding a photo ID can compute which of several thousand logical shards owns the row — routing falls out of arithmetic, no lookup table required. The experiment mints a stream of IDs across eight shards and then checks both claims against the raw integers.

What time-sortable IDs buy the scroll

Here's the payoff hiding in every infinite feed. Paginating with OFFSET 2000 LIMIT 20 forces the database to walk and discard two thousand rows to serve twenty — the deeper the scroll, the more work per page. But if IDs sort by time, the app can instead remember the last ID it showed and ask WHERE id < cursor ORDER BY id LIMIT 20: an index seek straight to the cursor, twenty rows read, at any depth. The experiment scrolls one user down the same feed both ways and counts the rows the database actually touches.

The rest of the boring-technology gospel

The famous stack around that number was deliberately dull: nginx, Django, PostgreSQL behind pgbouncer (a raw Postgres connection cost ~1.3 MB — pooling wasn't optional), Redis for the precomputed feeds (fan-out-on-write, the same family we proved in the Twitter episode), memcached, S3 for the bytes. When a 300-million-entry Redis mapping got heavy, they didn't build a database — they repacked it into Redis hashes and cut 21 GB to 5. Fourteen million users, terabytes of photos, a hundred-plus instances: three engineers. At the $1B acquisition it was thirty million users and thirteen employees, and the later "Instagration" moved twenty billion photos from AWS into Facebook's datacenters — with roughly eight engineers and no user-visible downtime.

Two epilogues tie back into the series. In 2016 the chronological feed died a data-driven death — users were missing ~70% of posts, so an ML ranker took over and pushed "posts seen from friends" to ~90%: the same pool-then-rank shape as Twitter's funnel. And in 2018 Instagram attacked tail latency the hard way: Rocksandra swapped Cassandra's Java storage engine for C++ RocksDB, cutting GC stalls from 2.5% to 0.3% — a 10× P99 win, the Tail at Scale lesson applied with a soldering iron. The keeper from this episode is smaller and sharper: when you can, design the data so the infrastructure becomes unnecessary. The best ID service is a number that already knows everything the service would have said.
