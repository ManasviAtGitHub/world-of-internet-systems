The Skip List

A linked list that bought itself binary search with a coin. Every node flips for extra height, tall nodes become express lanes, and suddenly a structure with no rotations, no rebalancing, and no rules beyond "keep each lane sorted" answers in O(log n). It's what Redis chose for every leaderboard and sorted set on earth, and what RocksDB runs as the memtable inside the LSM tree you already met. The balance isn't maintained — it's probable, and that turns out to be an upgrade. Predict first, then run it. That's the rep.

Everything below computes for real: the hero re-verifies its lane invariant every frame, the REP builds an actual million-entry skip list in typed arrays and counts every comparison of every search, and both duels run real structures on identical operation streams.

Pattern
sorted linked list · randomized express lanes · probabilistic balance
Space
O(n) — expected 2 pointers per node at p = ½
Time
search/insert/delete O(log n) expected · range scan = walk the base lane
The catch
the balance is a probability, not a guarantee — but the coins never look at your keys, so no input can rig them

Where the logarithm comes from

Read the lane census above: each lane holds about half the one below, so ~log₂ n lanes exist, and a search does a couple of hops per lane before dropping. No algorithm enforces that halving — the coin's ½ probability is the enforcement. So price it: a million entries in a skip list — how many comparisons does one search actually cost? The pure-binary-search instinct says log₂(1,000,000) ≈ 20. The linked-list doubter says you'll crawl half a million. Commit to a button; then this page builds a real million-entry skip list and runs two thousand real searches through it, counting every comparison.

The leaderboard, which is to say: Redis

Every "top players", "top posts", "top anything" list you've used runs on a sorted structure taking a firehose of score updates while staying instantly rankable — the Front Page episode's listings are this shape at planetary scale. Redis implements every sorted set as a skip list (paired with a hash for O(1) score lookups), and its author's stated reasons are exactly an interviewer's follow-ups: as fast as a balanced tree, far simpler to implement, and range operations are just a walk. The killer input, and why the coins don't care

The classic follow-up: "why not just a binary search tree?" Because a naive BST's shape is decided by your input order — and production input is rarely random. Feed it monotonically increasing keys (timestamps, auto-increment IDs — the most common keys in existence) and it degenerates into a linked list. Balanced trees fix this with rotations; the skip list fixes it by construction: its shape comes from coin flips the input never sees. The keeper

The keeper: a skip list is a sorted linked list that rents log n express lanes for two pointers a node — search ~2·log₂ n, no rotations ever, ranges as plain walks, and a balance that no adversarial input can rig because the coins are private. When the interview says leaderboard, sorted set, or "log n but simple," this is the shape; inside Redis and inside every LSM memtable, it already is.

The revision card — for the you that comes back in three months
  • Where does the log come from with no balancing code? (each lane keeps ~half the one below — the coin is the enforcement; you read the census)
  • What's the true search bill at a million entries? (~40 — 2·log₂ n; a hop per lane plus the drop, measured live)
  • Why did Redis pick it over a red-black tree? (same asymptotics, no rotation code, ranges are just walks — antirez said exactly this)
  • What kills a naive BST but not a skip list? (sorted input — the most common production keystream there is; the coins never see your keys)
