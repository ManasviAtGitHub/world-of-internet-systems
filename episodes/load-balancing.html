The Load Balancer

Every big site is thousands of ordinary computers pretending to be one. The pretence is maintained by machines that answer a single question, millions of times a second: which server should take this request? Choose badly and the site drowns. This page doesn't just tell you the good answer — it runs the experiments in front of you.

Every dot below is one request. Time is slowed enormously — real requests finish in milliseconds — and each simulation is honest: the queues, waits, and failures emerge from the same mathematics that governs real datacenters, not from a script.

First, watch one server die

Before any balancing, understand the enemy: the queue. A server is a worker at a desk. Requests arrive at random moments; each takes a random amount of effort. As long as work arrives more slowly than the desk clears it, all is calm. But push the arrival rate toward the desk's capacity and something vicious happens — waiting time doesn't rise gradually. It bends upward and explodes before you reach 100% utilization.

Queueing theory predicts the exact shape of that explosion: for random arrivals and random job sizes, time-in-system grows like 1/(1−ρ), where ρ is utilization. At 50% load a request takes 2× its ideal time. At 90% — 10×. At 99% — 100×. The simulation below doesn't know that formula. Drag the slider and watch its measured dots land on the theory curve anyway.

This curve is the reason load balancing exists. You can never run servers near full utilization and keep latency — so you buy many servers and spread the work. Now everything depends on how you spread it.

Round robin, and its betrayal

The obvious algorithm is round robin: deal requests like playing cards — server 1, 2, 3, … and around again. Perfectly fair in count. NGINX has shipped it as the default for two decades, and under one assumption it's fine: that servers and requests are identical.

They never are. A server gets a slow disk, a noisy neighbor, a garbage-collection pause. Below, eight servers run under round robin. Flip the switch to make server 5 quietly run at one-third speed — the balancer has no idea. Watch what fairness-in-count does to it. Then switch the algorithm to least-connections (send to whoever holds the fewest open requests) or two random choices, and watch the same overload drain away.

So just pick the least-loaded server? The herd says no

Least-connections looks like the endgame — always send to the emptiest desk. But it hides an assumption at least as dangerous as round robin's: that your load information is current. At scale it never is. Real sites run many independent balancer machines, each seeing a fraction of traffic, sharing load stats with a delay.

Now the failure is spectacular. Every balancer reads the same slightly-stale report — "server 7 is idle" — and every one of them sends its next burst to server 7. The mob crushes it, the next report crowns a new idlest server, and the mob moves there. Marc Brooker (AWS) showed in simulation that with delayed information, picking the global best is actually worse than picking randomly (Brooker, 2012). Below, routing decisions use a load snapshot that refreshes only every two seconds.

The absurdly good compromise: two random choices

Which brings us to one of the prettiest results in computer science. In 1996, Michael Mitzenmacher's PhD thesis analyzed a family of strategies for throwing n balls into n bins. Throw purely at random and the fullest bin ends up holding about log n / log log n balls. But peek at just two random bins and drop into the emptier one, and the fullest bin holds about log log n — an exponential improvement, from one extra glance (Mitzenmacher, 1996). A third glance barely helps at all. Two is the magic number.

Both panels below receive the identical arrival stream. Left throws blind; right peeks twice. Watch the tallest stacks separate.

This is not a toy result

Power of two choices is what the industry actually converged on. NGINX shipped it as "Random with Two Choices" in 2018, recommending it precisely for fleets of independent balancers where load data is stale. Envoy — the proxy inside most service meshes — uses P2C as its default least-request policy. Behind them sits the heavier machinery our next episodes cover: Google's Maglev has balanced every packet to Google since 2008, one commodity machine saturating a 10 Gbps link, using consistent hashing so that any Maglev can handle any packet of any flow. Cloudflare runs no dedicated balancer boxes at all — every edge server balances via anycast plus an in-kernel program costing under 1% CPU. GitHub's GLB stretches one IP across a fleet with rendezvous hashing.

Different scales, same lesson the experiments just proved: never trust one number you believe, when you can compare two you doubt. Fairness in count ignores reality; chasing the global best amplifies your own staleness; two random glances get you within sight of optimal, with no coordination at all.
