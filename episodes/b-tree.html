The B-Tree

The structure that has answered more queries than any other object in computing. Since 1972 it has organized nearly every relational database on earth — the MySQL under Airbnb's calendar, Shopify's checkouts, Pinterest's boards — on one insight: if a disk hands you a whole page anyway, make every node a page and every page a hundred-way decision. The tree gets shallower than seems possible, it grows upward instead of down, and a billion keys sit three or four page-reads deep. Predict first, then run it. That's the rep.

Everything below computes for real: real nodes splitting under real inserts, the every-leaf-at-one-depth invariant re-walked every frame, and the duel against the LSM tree runs both storage engines on the same operation stream with every page I/O counted.

The base of the logarithm

A binary tree makes one yes/no decision per node — and pays one memory (or disk) access for it. A B-tree page holds dozens of sorted keys, so one page read buys a 64-way decision. Same log, different base: log₂ costs you 21 levels for two million keys; log₆₄ collapses that to a handful. So price it: two million keys, pages holding up to 63 — how many page reads does one lookup cost? Commit; then a real two-million-key B-tree builds itself and two thousand real lookups count their pages.

The duel

This series has now built both of the great storage engines: the B-tree, which edits pages in place, and the LSM tree, which refuses to edit anything and pays compaction instead. Neither is "better" — they've split the database world between them (MySQL and Postgres on one side; Cassandra, RocksDB and friends on the other), and the dividing line is the read/write mix. Below, both engines are real, both eat the same operation stream, and every page of I/O is counted. You hold the mix dial. Find the crossover yourself.

The insert order you chose is a performance decision

Two identical B-trees, two key styles. One receives sequential keys — timestamps, auto-increment IDs — and only ever splits its rightmost page, which real engines optimize into near-full packing. The other receives random keys (UUIDs), splits everywhere, and settles at the textbook ~69% fill — a third more pages for the same data, forever. This is the folklore behind "don't use random UUIDs as primary keys," measured — and it's why the Feed episode's ID scheme went to such lengths to keep IDs time-sorted: their databases were B-trees, and the ID format was a storage-layout decision.

The keeper

The keeper: the B-tree makes the disk's page size the tree's branching factor — log-base-B lookups that put a billion keys three or four reads deep, a perfectly level floor maintained by splitting upward, ~69% fill under random keys and near-full under sequential ones — and its in-place page writes are the exact cost the LSM tree was invented to escape. Between this page and the LSM duel, you've now run both halves of the storage world's great fork.
